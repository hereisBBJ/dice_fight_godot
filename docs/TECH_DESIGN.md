# Dice Fight 技术策划书

## 1. 技术目标

本技术策划书用于指导基于《Dice Fight 玩法策划书》重新开发一个画面、功能相对完整，并支持局域网对战的游戏本体。

目标成品定位：

- 双人回合制骰子对战游戏。
- 具备完整角色选择、强化选择、战斗、结算、再来一局流程。
- 支持局域网内一名玩家开房，另一名玩家加入。
- 规则由主机统一结算，客户端只负责输入与表现。
- 规则、角色、技能、强化尽量数据驱动，便于后续扩展。

不优先追求：

- 公网匹配。
- 账号系统。
- 排位、战绩、商城等长期运营系统。
- 复杂实时同步。

## 2. 推荐开发模式

推荐使用 **Godot 4 + 主机权威房间制 + 数据驱动规则层**。

### 2.1 为什么推荐 Godot 4

本项目是 UI 和回合制规则驱动的 2D 游戏，Godot 4 的优势比较贴合：

- 2D UI、按钮、面板、动效、状态图标开发效率高。
- 可直接制作角色选择、战斗棋盘式界面、骰子动画和战斗日志。
- 内置多人联机能力，适合局域网 Host / Join。
- 项目体量轻，迭代速度快，适合从现有 Python 原型迁移到正式游戏本体。
- 资源、场景、脚本组织直观，后续新增角色和技能成本较低。

### 2.2 替代方案

| 方案 | 适用情况 | 不推荐作为首选的原因 |
| --- | --- | --- |
| Unity + Netcode | 未来要做更强商业化表现、复杂特效、跨平台发行 | 初期工程复杂度更高，对这个回合制项目略重 |
| Web 前端 + Node 服务端 | 想做浏览器游玩、无需安装客户端 | 本地资源、音效、打包体验和游戏手感需要额外投入 |
| Python + Pygame | 想保留 Python 生态、快速做 2D 原型 | UI、打包、资源管理和联网体验不如游戏引擎 |
| 继续 Python/Tkinter | 只做规则验证或内部测试 | 不适合作为画面完整的游戏本体 |

## 3. 总体架构

推荐架构：

```text
Godot 游戏本体
├─ 表现层
│  ├─ 角色选择界面
│  ├─ 强化选择界面
│  ├─ 战斗界面
│  ├─ 骰子、技能、状态、日志表现
│  └─ 胜负与再来一局界面
├─ 输入层
│  ├─ 选择角色
│  ├─ 选择强化
│  ├─ 重掷
│  ├─ 修改骰子
│  ├─ 使用技能
│  ├─ 跳过回合
│  └─ 交互判定确认
├─ 网络层
│  ├─ 创建房间
│  ├─ 加入房间
│  ├─ 指令上行
│  ├─ 状态快照下行
│  └─ 断线与重开处理
└─ 规则层
   ├─ 战斗状态
   ├─ 骰子需求校验
   ├─ 行动合法性校验
   ├─ 技能结算
   ├─ 状态结算
   ├─ 强化结算
   └─ 胜负判定
```

核心原则：

- **规则层独立**：不要把技能结算写死在按钮回调或动画里。
- **主机权威**：所有随机、扣血、扣蓝、状态变化都由主机结算。
- **客户端轻量**：客户端只提交意图，不自行判定最终结果。
- **状态快照同步**：主机每次关键变化后广播完整或半完整战斗状态。
- **表现可延迟**：先保证规则完整，再补动画和音效。

## 4. 联网设计

### 4.1 联网模型

采用 **Host / Client 局域网房间制**。

- 玩家 A 创建房间，同时成为主机。
- 玩家 B 输入主机局域网 IP 或房间信息加入。
- 主机保存完整战斗状态。
- 客户端保存展示用状态。
- 所有玩家操作都发送给主机，由主机验证后广播新状态。

### 4.2 为什么不用双端各算

本游戏存在大量随机与条件结算：

- 掷骰。
- 重掷。
- 修改骰子。
- 灼烧逐层判定。
- 闪避判定。
- 强化选择。
- 回合先后手。

如果双端各自结算，随机结果和边界规则很容易不同步。主机权威可以保证双方看到同一局游戏。

### 4.3 基础消息类型

推荐将网络消息分为两类：玩家指令和主机事件。

玩家指令：

| 指令 | 说明 |
| --- | --- |
| `create_room` | 创建房间。 |
| `join_room` | 加入房间。 |
| `select_character` | 选择角色。 |
| `pick_augment` | 选择强化。 |
| `reroll_dice` | 重掷本回合骰子。 |
| `modify_die` | 修改 1 个骰子的点数。 |
| `use_skill` | 使用技能，可携带普通、强化、锁定等模式。 |
| `skip_turn` | 跳过本回合。 |
| `interactive_response` | 闪避、灼烧、风炎投入等交互回应。 |
| `restart_request` | 请求再来一局。 |

主机事件：

| 事件 | 说明 |
| --- | --- |
| `room_joined` | 加入房间成功，返回玩家编号。 |
| `state_snapshot` | 广播当前游戏状态。 |
| `battle_log` | 广播战斗日志。可并入状态快照。 |
| `ask_interactive` | 要求指定玩家进行交互判定或输入。 |
| `phase_changed` | 阶段切换。可并入状态快照。 |
| `game_over` | 对局结束。可并入状态快照。 |
| `error_message` | 操作不合法或连接异常提示。 |

### 4.4 同步策略

推荐 MVP 阶段直接使用 **完整状态快照同步**。

每次以下事件发生后，主机广播状态快照：

- 玩家选角。
- 玩家选择强化。
- 开始战斗。
- 重掷。
- 修改点数。
- 玩家提交行动。
- 回合结算完成。
- 状态伤害结算完成。
- 游戏结束。
- 再来一局重置。

完整快照的好处：

- 实现简单。
- 不容易出现漏同步。
- 便于调试。
- 回合制游戏数据量小，不会造成明显网络压力。

后续如需要优化，再改为增量事件同步。

## 5. 游戏状态设计

### 5.1 对局阶段

建议使用清晰的阶段状态机：

| 阶段 | 说明 |
| --- | --- |
| `lobby` | 等待玩家进入房间。 |
| `character_select` | 双方选择角色。 |
| `augment_select` | 双方选择强化。 |
| `battle` | 正常战斗回合。 |
| `resolving` | 双方已提交行动，主机正在结算。 |
| `interactive` | 等待某玩家完成闪避、灼烧、风炎等交互。 |
| `game_over` | 对局结束。 |

阶段切换只允许由主机发起。

### 5.2 玩家状态

每名玩家建议保存：

```text
PlayerState
- player_id
- character_id
- hp
- max_hp
- mp
- max_mp
- shield
- max_shield
- dice[4]
- has_modified_this_turn
- submitted_action
- buffs[]
- augments[]
- per_turn_flags
- per_game_flags
- damage_taken_this_turn
- damage_taken_last_turn
- dealt_damage_this_turn
- dealt_damage_last_turn
```

### 5.3 战斗状态

全局战斗状态建议保存：

```text
BattleState
- phase
- round
- first_player_id
- players[2]
- pending_actions
- pending_interactive_request
- logs[]
- random_seed_or_rng_state
```

MVP 阶段不强制暴露随机种子，但所有随机必须只在主机发生。

## 6. 数据驱动设计

### 6.1 推荐数据文件

建议把大部分数值配置放入数据文件：

```text
data/
├─ characters/
│  ├─ berserker.json
│  ├─ mage.json
│  ├─ gambler.json
│  ├─ witch.json
│  ├─ assassin.json
│  ├─ swordsman.json
│  ├─ arcanist.json
│  ├─ archer.json
│  └─ pyromancer.json
├─ augments_common.json
├─ augments_character.json
└─ status_effects.json
```

如果使用 Godot，也可以用自定义 Resource 替代 JSON。早期推荐 JSON，便于从现有 Python 数据迁移和人工编辑。

### 6.2 角色数据

角色数据应包含：

- 角色 ID。
- 展示名称。
- 初始 HP / 最大 HP。
- 初始 MP / 最大 MP。
- 护盾上限。
- 主题色。
- 立绘资源路径。
- 被动 ID 与参数。
- 技能列表。

### 6.3 技能数据

技能数据应包含：

- 技能 ID。
- 技能名称。
- 技能类型：攻击或防御。
- MP 消耗。
- 骰子需求。
- 描述文本。
- 图标资源路径。
- 效果列表。
- 可选特殊模式：强化施法、锁定攻击、数值输入等。

示例结构：

```json
{
  "id": "swordsman_shield_bash",
  "name": "盾击",
  "type": "attack",
  "cost": 20,
  "dice_requirements": [6, "1-3"],
  "effects": [
    {
      "type": "damage_by_shield",
      "base": 20
    }
  ]
}
```

### 6.4 特殊技能处理

不要为了完全数据化而把所有特殊技能做成复杂脚本表达式。建议采用折中方案：

- 普通伤害、护盾、治疗、加状态、回蓝等用数据效果描述。
- 特殊技能使用 `effect.type` 映射到规则层中的专用处理器。
- 处理器只负责规则，不负责 UI 和动画。

示例：

| 效果类型 | 用途 |
| --- | --- |
| `damage` | 固定伤害。 |
| `shield` | 获得护盾。 |
| `heal` | 回复生命。 |
| `add_status` | 添加状态。 |
| `damage_by_shield` | 剑士盾击。 |
| `damage_by_last_taken` | 剑士终结。 |
| `mana_siphon_damage` | 奥术师汲取。 |
| `consume_all_mp_damage` | 奥术师风暴。 |
| `evasion_attack` | 弓箭手射击。 |
| `backstep` | 弓箭手后跳。 |
| `variable_burn` | 炎术师风炎。 |

## 7. 规则层设计

规则层建议拆成以下模块：

| 模块 | 职责 |
| --- | --- |
| `DiceRules` | 掷骰、骰子需求匹配、重掷、修改点数。 |
| `ActionValidator` | 判断玩家当前能否使用技能、跳过、重掷、修改。 |
| `TurnManager` | 回合开始、双方提交、结算顺序、先后手切换。 |
| `EffectResolver` | 伤害、护盾、治疗、回蓝、状态添加等通用效果。 |
| `SkillResolver` | 根据技能效果列表调用具体结算。 |
| `StatusResolver` | 中毒、灼烧、免疫、必定闪避、格挡等状态规则。 |
| `AugmentResolver` | 强化选择、强化数值修正、回合内强化次数标记。 |
| `PassiveResolver` | 角色被动触发。 |
| `BattleLog` | 生成玩家可读战斗日志。 |

### 7.1 行动结算流程

推荐固定流程：

1. 主机收到双方行动。
2. 战斗阶段切到 `resolving`。
3. 先执行先手玩家行动。
4. 若后手玩家仍存活，执行后手玩家行动。
5. 结算回合末效果。
6. 判断胜负。
7. 若未结束，切换下一回合先后手。
8. 开始下一回合，重新掷骰。
9. 结算回合开始状态。
10. 广播新状态快照。

### 7.2 交互判定流程

部分技能或状态需要玩家二次决策，例如：

- 闪避判定是否重掷或修改。
- 灼烧判定是否重掷或修改。
- 风炎投入多少 MP。
- 强化施法或锁定攻击是否启用。

推荐做法：

- 技能释放前的可选模式，例如强化施法、锁定攻击，在客户端选择技能时确定。
- 结算中的判定，例如闪避和灼烧，由主机发起 `ask_interactive`。
- 被询问玩家返回 `interactive_response`。
- 主机继续结算。
- 如果玩家超时，使用默认确认或取消策略。

默认策略建议：

| 交互 | 超时默认 |
| --- | --- |
| 闪避/灼烧判定 | 接受当前骰面，不重掷不修改。 |
| 风炎投入 | 取消施法或投入最小值，二选一需在实现前固定。推荐取消施法。 |
| 强化施法/锁定攻击 | 不启用。 |
| 强化选择 | 按候选顺序自动补足。 |

## 8. UI 与表现设计

### 8.1 必要界面

MVP 至少需要以下界面：

- 主菜单：创建房间、加入房间、输入 IP。
- 房间等待：显示玩家编号、连接状态。
- 角色选择：角色列表、属性、技能预览。
- 强化选择：通用强化选择、角色专属强化选择。
- 战斗界面：双方状态、骰子、技能、操作按钮、战斗日志。
- 交互弹窗：闪避、灼烧、风炎投入等。
- 结算界面：胜利/失败、再来一局。

### 8.2 战斗界面布局

推荐布局：

```text
┌────────────────────────────────────┐
│ 对手角色区：HP / 护盾 / 状态 / 骰子 │
│                                    │
│              战斗表现区             │
│                                    │
│ 自己角色区：HP / MP / 护盾 / 状态   │
├────────────────────────────────────┤
│ 自己骰子 │ 技能按钮 │ 重掷/修改/跳过 │
├────────────────────────────────────┤
│ 战斗日志                           │
└────────────────────────────────────┘
```

### 8.3 表现优先级

建议按以下顺序做表现：

1. 静态 UI 可用。
2. 骰子显示和按钮状态正确。
3. 战斗日志清晰。
4. 状态图标和悬浮说明。
5. 技能释放动效。
6. 骰子滚动动画。
7. 音效和受击反馈。
8. 角色立绘差异化。

画面完整不等于一开始就要重动画。回合制游戏最先要保证信息清晰。

## 9. 开发里程碑

### 9.1 Milestone 1：单机规则闭环

目标：不用联网，同一客户端内控制 P1/P2 跑完整对局。

包含：

- 加载角色、技能、强化数据。
- 双方选角。
- 强化选择。
- 掷骰、重掷、修改。
- 攻防技能限制。
- 跳过回蓝。
- 完整回合结算。
- HP、MP、护盾、状态、胜负。
- 战斗日志。

验收标准：

- 9 个角色均可完成一局。
- 玩法策划书中的所有技能效果可触发。
- 不需要联网也能稳定测试规则。

### 9.2 Milestone 2：局域网 Host / Join

目标：一台机器创建房间，另一台机器加入并对战。

包含：

- 创建房间。
- 加入房间。
- 玩家编号分配。
- 指令发送。
- 主机校验与结算。
- 状态快照同步。
- 基础断线提示。

验收标准：

- 两台同局域网设备可完成至少 1 局完整对战。
- 双方状态、日志、骰子显示一致。
- 客户端不能通过非法按钮操作改变主机状态。

### 9.3 Milestone 3：表现完善

目标：让游戏本体具备可展示的完整度。

包含：

- 角色立绘。
- 技能图标。
- 状态图标。
- 骰子动画。
- 受击、护盾、治疗、灼烧、中毒反馈。
- 胜负界面。
- 基础音效。

验收标准：

- 玩家不看日志也能理解主要战斗变化。
- 关键状态有明确视觉提示。
- 技能按钮说明足够清楚。

### 9.4 Milestone 4：可维护化

目标：让后续新增角色和技能不痛苦。

包含：

- 数据校验工具。
- 自动化规则测试。
- 战斗回放或日志导出。
- 调试面板。
- 角色/技能数据模板。

验收标准：

- 新增普通伤害/护盾类技能无需改 UI。
- 新增角色可通过数据文件完成大部分配置。
- 关键规则有测试覆盖。

## 10. 测试策略

### 10.1 规则测试

优先为纯规则层写测试：

- 骰子需求匹配。
- 护盾抵消和破盾。
- 跳过回蓝。
- 重掷和修改消耗。
- 强化消耗修正。
- 灼烧判定。
- 中毒持续。
- 免疫、必定闪避、格挡。
- 每个角色的核心技能。
- 死亡保护和急救本能。

### 10.2 联网测试

至少覆盖：

- 本机双开连接。
- 两台局域网设备连接。
- 客户端断线。
- 主机断线。
- 非当前阶段发送指令。
- MP 不足时尝试使用技能。
- 骰子不满足时尝试使用技能。
- 双方同时提交行动。

### 10.3 表现测试

至少检查：

- 技能按钮是否正确禁用。
- 当前先手/后手是否明确。
- 对手骰子信息是否按设计展示。
- 状态图标是否与状态列表一致。
- 战斗日志是否能解释结算结果。
- 游戏结束后是否能再来一局。

## 11. 开发注意事项

- 不要让客户端直接扣血、扣蓝或生成最终随机结果。
- 不要把角色特殊规则散落在 UI 按钮里。
- 不要在动画播放完成后才改变核心状态；应先由规则层结算，再由表现层播放结果。
- 不要过早做复杂匹配系统；局域网 Host / Join 足够支撑第一版。
- 不要追求 100% 数据化技能脚本，特殊技能可以通过规则处理器承接。
- 战斗日志要从第一版就保留，它是调试规则和玩家理解结算的关键工具。

## 13. 与玩法策划书的关系

玩法策划书负责回答：

- 游戏怎么玩。
- 每个角色有什么技能。
- 每个状态和强化如何生效。
- 回合如何结算。

本技术策划书负责回答：

- 用什么技术形态做。
- 规则如何组织。
- 联网如何同步。
- UI 和数据如何拆分。
- 先做哪些里程碑。

开发时建议顺序：

1. 以玩法策划书为规则来源。
2. 以本技术策划书搭建工程结构。
3. 先完成单机规则闭环。
4. 再接入局域网联机。
5. 最后补足表现和体验。
